**Owner-гипотеза:** разметка приходит неправильная из-за того, что кеш отдаёт
переводы, не соответствующие текущей раскладке документа. Гипотеза не
опровергнута и не подтверждена — ниже приведены пять конкурирующих версий и
решающий эксперимент для каждой.

**Tickets:** DT-104–DT-107. Исполнение и поправки к исходным предположениям:
[доказательный отчёт](2026-10-04-pdf-layout-root-cause-execution.md).

> `pdf_render_completed` уже логирует fallback, старый шестистраничный PDF
> частично теряет текст, а неполный набор переводов может удалять оригинал
> через пересекающиеся bbox. Актуальные выводы находятся в отчёте.

`app/core/services/cache_keys.py` начинает ключ с `target_language`. Немецкий,

`diag-01.docx`: `triage_status=ok`, `source_language=ru`,

Ранее все 9 анализов в базе были `degraded`.

### 1.5 Найдена конкретная причина 45 страниц — и она НЕ в кеше

Прогон реального алгоритма влезания (`insert_textbox`, тот же шрифт, тот же
цикл уменьшения) по 70 блокам `platon-gliph.pdf` с текущим английским переводом:

```
влезают: 28 | уходят в fallback: 42 (60%)
```

Bbox — однострочные рамки высотой 16–30 pt. Английский текст длиннее русского,
лишние строки уходят на новые страницы через `_append_paginated_text`
(`app/adapters/formats/pdf.py:236-245`). 42 блока → 42 страницы. Это
спроектированный fallback, а не регрессия.

### 1.6 Утечка управляющих кодов — 1 блок

```
seq=4  'Ключевые идеи\n\x01🏛️\x02'
```

`U+0001`/`U+0002` присутствуют в `source_text` после извлечения. Этот блок
деградирует по DT-77 и **остаётся в исходном виде**, тогда как соседние блоки
переведены. На странице это даёт ровно наблюдаемую картину:
`'Ключевые идеи \x01🏛️\x02 Plato Plato Key Ideas justice and justice and …'`.

### 1.7 Устаревший документ против свежей выемки — **подтверждено**

`platon-gliph.docx`, один и тот же файл:

| | блоков | в таблицах |
|---|---:|---:|
| свежая выемка `DocxExtractor` | **44** | **28** |
| сохранено в БД (doc `96b1f435`) | **16** | **0** |

`document_id = sha256(байтов файла)`, поэтому повторная загрузка возвращает
существующий документ и **не переизвлекает блоки** (`document_service.py`,
ветка «existing»). `DELETE`-эндпоинта нет.

## 2. Конкурирующие гипотезы

| | Гипотеза | Статус | Решающий эксперимент |
|---|---|---|---|
| **H1** | **Кеш подмешивает переводы блокам с чужой раскладкой** | не проверена | Фаза 2, шаг 1 |
| **H2** | **Устаревший документ**: блоки в БД старше кода, раскладка не та | **подтверждена частично** (1.7) | Фаза 2, шаг 3 |
| **H3** | **Смешанная разметка из-за деградации DT-77**: один блок с эмодзи остаётся русским среди английских | **подтверждена** (1.6) | Фаза 2, шаг 4 |
| **H4** | **Неограниченный fallback PDF** — 42 страницы | **подтверждена** (1.5) | Фаза 2, шаг 5 |
| **H5** | **Метаданные теряются при round-trip через БД** | не проверена | Фаза 2, шаг 2 |

H1 — приоритетная гипотеза владельца, и у неё есть конкретный механизм: кеш
глобален (ключ `translation_key` + `source_hash`) и не несёт разметки. Если
документ в БД устарел (H2), то `source_hash` его блоков совпадают со строками
кеша, записанными для **другого** набора блоков, и переводы приземляются на
старую раскладку. H1 и H2, вероятно, связаны.

"""Probe: does the render differ between cache-sourced and directly-fed text?"""

from app.adapters.formats.pdf import PdfRenderer
from app.adapters.persistence.repositories import SqliteTranslationCacheRepository
from app.core.services.cache_keys import translation_key


async def test_cache_sourced_and_direct_translations_render_identically(tmp_path, ...):
    connection = await make_connection(tmp_path)          # написать самому
    cache_repo = SqliteTranslationCacheRepository(connection)
    blocks = await repo.get_blocks(document_id)            # DocumentRepository

    key = translation_key(job.target_language, job.model, job.prompt_version, job.glossary, plan)

    # Путь A: ровно то, что делает прод-код (app/worker/translation_loop.py:86).
    from_cache: dict[str, str] = {}
    for block in blocks:
        text = await cache_repo.get_block_translation(key, block.source_hash)
        if text is not None:
            from_cache[block.id] = text

    # Путь B: те же строки, поданные напрямую, кеш вообще не участвует.
    direct = dict(from_cache)

    a = await PdfRenderer().render(source, blocks, from_cache, tmp_path / "a.pdf")
    b = await PdfRenderer().render(source, blocks, direct,     tmp_path / "b.pdf")
    assert a.output_path.read_bytes() == b.output_path.read_bytes()
```

## 7. Инварианты расследования

1. **Ни одного коммита в фазах 1–3.** Только тесты и измерения.
2. **Не «чинить» кеш, пока не доказано, что он виноват.** Правка H4 не должна
   выглядеть как починка разметки.
3. **Провайдер не вызывается.** Все переводы берутся из кеша или из уже
   существующих выходных файлов.
4. **Никаких записей в `/data/app.db`** до Фазы 5. Расследование читает.
4. **Артефакта `worker_render_completed` не существует.** Проверено: в коде есть
   только `worker_render_degraded` (`assembly.py:94`, поля
   `degraded_block_count`, `degraded_block_ids`) и `worker_render_failed`
   (`claim_loop.py:152`). Никакого события об успешном рендере нет.
5. **Метрики влезания вычисляются и молча теряются.** `RenderResult` несёт
   `fallback_blocks` и `fallback_pages` (`core/models.py:68`), но вне
   `pdf.py` эти поля **не читаются нигде**: grep даёт только `pdf.py:146-153`.
   Они не логируются и не сохраняются. Поэтому у вас не было ни одного
   сигнала о том, что 42 блока уехали на отдельные страницы, — данных нет
   не «не смотрели», их не существует. `passthrough_block_ids` при этом
   читается в `assembly.py:82`, то есть прецедент есть.
6. **Управляющие коды не «чинить» в логах** — они в `source_text`, это данные
   документа, а не диагностика.

Значения, которые нужно уметь воспроизвести; расхождение с ними = новая причина.

```

Блоков с управляющими кодами:              1      (seq=4, 'Ключевые идеи\n\x01🏛️\x02')

Таймлайн для привязки к коммитам:

```
15:39  e3ba009  DT-77   последний коммит pdf.py — рендер с тех пор не менялся
19:43  8f52460  DT-89   Markdown + structural bypass
21:00  af889892  en → 6 страниц, но перевода на страницах нет
21:57  3f9fff4  DT-91   миграция УДАЛЯЕТ таблицу block_translations
00:31  a40c752c  en → 45 страниц, перевод на страницах есть
```

`3f9fff4` попадает в окно между последним «нормальным» и первым «сломанным»
выводом, но **не является причиной**: `pdf.py` и `assembly.py` он не трогал,
а прогон `diag-01.docx` доказал, что кеш после него работает корректно.

### Почему нельзя опереться на логи рендера

События успешного рендера не существует, а счётчики влезания теряются
(см. инвариант 4–5 в разделе 7). Поэтому «посмотреть в лог и понять, что
произошло» для этой задачи **невозможно** — придётся измерять заново. Это
само по себе дефект наблюдаемости и кандидат на отдельный маленький тикет.

## 9. Вне области

- Политика fallback и порог `render_failed` (H4) — продуктовое решение.
- Семантический/векторный кеш, fuzzy-матчинг.
- Качество перевода и метрики качества.
- Кеширование артефактов сборки (собранного PDF целиком).
- Любые правки `app/worker/translation_loop.py` и `app/worker/assembly.py` до
  доказанной причины.

## 10. Заметки по исполнению

- Фаза 1 полностью локальна: тесты без БД, без провайдера, без сети.
- Логи воркера **стираются при каждом рестарте контейнера** — это уже стоило
  расследования; снимайте их до, а не после.
- Усреднение по нескольким языкам вводит в заблуждение: de и en для одного
  документа используют разные ключи кеша, и «6 против 45 страниц» сравнивает
  разные наборы переводов, а не разное качество влезания.
- Если Фаза 1 покажет, что подтвердились только H3 и H4, честный ответ
  владельцу: **разметка не ломается**, документы просто долго переводились
  незаметно, а 45 страниц — это работающий fallback на узких bbox.
