## Corrected premises

Three items in the original cleanup instruction did not survive verification.

**`sqlalchemy[asyncio]` was load-bearing.** The ORM was genuinely unused, but its
extra is the only source of `aiosqlite`, which is imported directly by
`app/api/dependencies.py`, `app/adapters/persistence/database.py`,
`app/adapters/persistence/api.py` and `app/adapters/persistence/repositories.py`.
Removing the requirement as written would have uninstalled `aiosqlite` and broken
the whole persistence adapter. Applied instead: `uv remove sqlalchemy[asyncio]`
followed by `uv add aiosqlite>=0.22.1`, so the dependency is declared directly by
the modules that use it. `sqlalchemy` and `greenlet` were uninstalled; `uv.lock`
shrank by 49 lines.

**`sqlalchemy[asyncio]` was not in `AGENTS.md`.** The file said
`SQLAlchemy 2.0 (async, aiosqlite)`, a different string that was also wrong.
Corrected to `aiosqlite (raw SQL, no ORM)`, which matches the actual design.

**Triage is not unrecoverable from `analyzing`.** `app/adapters/persistence/triage.py`
documents an explicit recovery path: the claim query admits `status IN
('uploaded', 'analyzing', 'extracted')`, and its docstring states that `analyzing`
is eligible for recovery only because the caller already holds the cross-process
lock, so a live owner cannot be reclaimed. `app/mcp_server/server.py` records the
same trade-off next to its timeout path. DECISIONS.md documents the real
limitation — recovery is event-driven, not automatic.
